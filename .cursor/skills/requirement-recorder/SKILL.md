# 新需求记录与开发分流 Skill

本 Skill 负责在用户提出需求时进行**分流**：先确认是否为新需求，再决定"记录"还是"直接修改"。

## 核心流程（必须严格遵守）

收到用户的需求消息时，**无论需求内容是什么，第一步永远是确认"这是否是一个新需求"，不得跳过、不得替用户假设**。

### 第一步：确认是否为新需求

先询问用户，例如：

> 这是一个新需求吗？我需要先确认一下，以便决定是**记录到 `requirements/` 目录**（新需求），还是**直接修改代码**（存量修改）。

- 用户回答 **"是" / "新需求"**（或明确表达"记录需求"、"新增功能"等）→ 进入第二步（记录新需求）
- 用户回答 **"不是" / "存量修改"**（或明确表达"修改"、"优化"、"修复"、"调整"等）→ 进入第三步（直接修改）
- 若用户已明确说出"这是新需求"或"记录一下"，视为已回答，无需重复询问，直接记录。

### 第二步：记录新需求（写入 requirements/ 目录）

1. **落盘位置**：项目根目录的 `requirements/`（与 `todo/` 历史文档区分，新需求一律记到这里）。
2. **文件命名**：按日期命名，同日多批需求追加后缀区分：
   - `requirements/YYYY-MM-DD-功能描述.md`
   - `requirements/YYYY-MM-DD-功能描述-资金变动.md`
3. **格式**：严格参考 `requirements/_template.md`（总目标 / 需求清单 / 执行顺序 / 交付与验收口径）。
4. **记录规则**：
   - 每个需求以 `1、2、3...` 编号，一条一议，方便逐项落实；
   - 涉及新增字段/接口变更，必须写清**字段名、接口地址、APIfox 链接**（项目铁律：APIfox 驱动，杜绝主观臆测）；
   - 对"后端可能未提供字段/接口"的项显式标记风险（**待后端** / **待联调**）；
   - 涉及金额的逻辑必须使用 `mathjs`（记录时标注）。
5. **记录完成后**：向用户复述所记内容，确认无误后再结束本轮（记录阶段**不做任何代码修改**）。

### 第三步：直接修改（存量需求）

按项目开发规范直接实施修改，无需写入 `requirements/`：

1. 先检索库内现存逻辑（组件、方法、常量、mixins）尽量复用，禁止重复造轮子；
2. 接口/字段以 APIfox 文档为准，不主观臆测；
3. 金额相关计算必须使用 `mathjs` 保证精度；
4. 遵守 Vue 2 + Options API + JavaScript 语法限制（不用 TS/Vue3），单文件不超过 500 行；
5. **每次修改文件，必须在被修改文件的顶部添加"变更记录"注释**，说明本次改了什么（格式见下）；
6. 修改完成后向用户汇报改动内容与验证方式。

## 文件顶部变更注释规范（必须遵守）

**凡是修改了某个文件，都必须在该文件顶部（第一个标签/语句之前）添加变更记录注释**，格式如下：

```vue
<!--
	变更记录（每次需求变更在此追加，最新在上；格式：日期 - 改了什么）：
	- [YYYY-MM-DD] 本次改动说明（一句话讲清改了什么、为什么）。
	历史：
	- [YYYY-MM-DD] 历史改动说明。
-->
```

```javascript
/**
 * 变更记录（每次需求变更在此追加，最新在上；格式：日期 - 改了什么）：
 * - [YYYY-MM-DD] 本次改动说明。
 * 历史：
 * - [YYYY-MM-DD] 历史改动说明。
 */
```

规则：
- **新增文件**：同样在顶部带一条 `[日期] 新建` 变更记录；
- **追加不覆盖**：新变更记录加在最上方，已有记录保留为"历史"，不删除；
- **说明要可追溯**：写清"改了什么"（功能/字段/样式/修复），涉及接口注明接口名；
- **纯注释/格式化类改动**也需记录（如"新增字段说明注释"）。

## 记录规范速查（摘自 requirements/README.md）

| 事项 | 要求 |
|------|------|
| 目录 | `requirements/`（新需求第一落点） |
| 命名 | `YYYY-MM-DD-功能描述.md`，同日多批加后缀 |
| 模板 | `requirements/_template.md` |
| 验收口径 | `已实现` / `待后端` / `待联调` / `待确认是否需求` |
| 字段为空定位 | `后端未返回` / `前端字段映射错误` / `展示格式化错误` |
| 按钮缺失结论 | `回归缺陷` / `历史未实现` |

## 注意事项

- **必须询问，不要猜测**：即使用户表述很像新需求或很像修改，未确认前不得进入记录或修改流程。
- 记录与修改是**互斥**的两条路：新需求只记录不改代码；存量修改只改代码不记录。
- 同一天的多批新需求合并到当日文件，用编号区分，不重复建文件。
- 若用户明确指定"记录到 xxx 文件"或"记录到 xxx 目录"，以用户指定为准。
